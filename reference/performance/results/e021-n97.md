# E021 Intel N97 x86 message-load folding audit

Date: 2026-08-06  
Environment: Intel N97, Linux, CPU 3 pinned, AVX2 (`UseAVX=2`,
`MaxVectorSize=32`), stock and E019-patched OpenJDK 28-internal.

## Hypothesis

Rust can use a memory operand directly in an x86 vector add. If C2 instead
materialized every BLAKE3 message vector with a separate `vmovdqu`, those loads
might add enough instructions and live temporaries to explain both the N97's
4.28x Java/Rust instruction ratio and the pressure from 18 conceptual vector
values against 16 architectural registers.

This mechanism is x86-specific. AArch64 NEON does not have the same arithmetic
memory-operand form, so the N97 evidence cannot diagnose the Apple M5 gap.

## Counting corrections

Three details are necessary before interpreting grep counts:

1. The compact Java source retains a seven-iteration round loop. It has 16
   static message loads, not 112. Those 16 execute seven times, producing 112
   dynamic message loads per block.
2. `Blake3ChunkVectorScratch` uses `IntVector.SPECIES_128`, so its registers are
   XMM. A grep ending in `%ymm` reports zero even when separate loads exist.
3. E018's approximately 4,720-byte body is the isolated
   `sevenRoundsLoop` benchmark. The production `hashChunks` compilation being
   audited is approximately 7,648 bytes on stock JDK 28 and 7,864 bytes after
   E019.

The useful patterns must also distinguish message-array loads from `%rsp`
spill traffic. In the annotated AT&T syntax used here, message accesses have
the array-base form `0xc(base,index,4)`:

```text
rg -c 'vpaddd\s+0xc\([^)]*,4\)' build/e021-stock-four-perfasm.log
rg -c 'vmovdqu\s+0xc\([^)]*,4\),%xmm' build/e021-stock-four-perfasm.log
```

The same patterns were applied to the E019-patched capture
`build/e020-four-perfasm.log`.

## Static and dynamic result

| stable non-OSR round body | stock JDK | E019 JDK |
|---|---:|---:|
| folded message-source `vpaddd` | **8** | **8** |
| separate message `vmovdqu` | **8** | **8** |
| total static message reads | 16 | 16 |

The split is therefore exactly half, and E019's rotate rule does not change it.
For each block:

| dynamic message reads | count |
|---|---:|
| folded: 8 x 7 rounds | 56 |
| separate: 8 x 7 rounds | 56 |
| total | 112 |

Across the 16 blocks in one four-chunk batch, that becomes 896 folded and 896
separate message reads.

The result is neither proposed extreme. Folding is not absent, but it is not
complete. One of each G's two message operands is already consumed by a
memory-source add; the other is materialized in a temporary register.

## Quantitative ceiling

The E020 stock exact run retires 37,900.635 instructions per four-chunk batch.
Assuming optimistically that every one of the 896 remaining loads can disappear
without adding address, bounds, scheduling, or spill work:

```text
896 / 37,900.635 = 2.36%
```

The corresponding patched ceiling is 896 / 37,033.387 = 2.42%. This is an
upper bound on retired instructions, not a predicted time gain.

E017 measured 89.83M Java instructions and 20.99M Rust instructions per 8 MiB
hash. The update path executes 2,047 four-KiB SIMD batches and retains the final
batch for correct rightmost-chunk finalization, so the remaining separate loads
contribute at most:

```text
896 x 2,047 = 1,834,112 instructions
```

That is 2.04% of Java's total and 2.67% of the 68.84M-instruction Java/Rust
excess. Removing every one would change the ratio from 4.28x to only:

```text
(89.83M - 1.834M) / 20.99M = 4.19x
```

Even the false counterfactual in which none of the 112 message reads folded
would account for only 3.668M instructions, or 5.33% of the Java/Rust excess.
Message-load folding therefore cannot explain the N97 sitting near half of
Rust throughput or Java retiring 4.28x Rust's instructions.

## Register-pressure interpretation

The result also breaks the proposed single mechanism for register pressure.
The source names 16 state vectors plus `mx` and `my`, but those names do not
mean 18 vector registers stay simultaneously live. Half the message operands
never occupy a vector register at all, and each separate operand is a
short-lived temporary consumed by its following add. Spill traffic remains
real, but it cannot be attributed simply to two permanently live message
vectors. The 16 state values, rotate temporaries, scheduling, and surrounding
block-loop state still need to be considered.

## Decision

Reject missing x86 memory-operand folding as a primary explanation and retire
source restructuring whose sole goal is to fold the remaining message loads.
Its best-case instruction reduction is about 2.4%, far below the measured gap;
composition and code-shape risks from E013, E016, and E018 are larger than that
ceiling.

The audit does not diagnose Apple M5 performance. The README's 63%-of-Rust M5
figure is a historical E011 comparison, and AArch64 lacks the x86 arithmetic
memory-operand mechanism tested here. M5 needs an independent instruction-class
and generated-code audit before assigning its remaining gap to any N97 cause.
