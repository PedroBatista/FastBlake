# E019 Intel N97 custom-JDK AVX2 rotate lowering

Date: 2026-08-06  
Environment: Intel N97, Linux, CPU 3 pinned, `kernel.perf_event_paranoid=2`,
OpenJDK 28-internal built from `c61f5b7ad8f`, AVX2 (`UseAVX=2`,
`MaxVectorSize=32`). The unmodified comparison VM is
`/opt/jdk-28-custom`; the experimental image is
`/home/pedro/bin/jdk/jdk/build/linux-x86_64-server-release/jdk`.

## Question

E016 showed that Rust lowers BLAKE3's packed ROR8/ROR16 to `vpshufb` while
Java used shift/shift/OR for all four rotate counts. E018 then showed that
duplicating Java Vector API source is not viable. E019 asks whether preserving
the compact Java graph and changing C2 instruction selection can close a useful
part of the N97 gap.

## HotSpot experiment

The x86 matcher now keeps constant 128/256-bit `RotateRightV` nodes for `int`
lanes when `UseAVX == 2`. A new rule emits:

- one memory-source `vpshufb` for ROR8 and ROR16;
- the existing `vpslld`/`vpsrld`/`vpor` sequence for other non-zero counts;
- a vector move for a zero count.

Two 32-byte shuffle masks are generated in the compiler-stub area, duplicated
for both 128-bit lanes of an AVX2 register. Variable rotates still degenerate
on pre-EVEX x86. The existing EVEX immediate-rotate rule now has an explicit
EVEX/AVX512VL predicate; previously it relied on earlier graph degeneration to
make it unreachable on AVX2.

## Correctness and allocator failures found during development

The first matcher version allowed the old EVEX-only rule to compete with the
new AVX2 rule. C2 selected it and the N97 raised `SIGILL` in an OSR compilation
of `Blake3ChunkVectorScratch.hashChunks`. Adding the explicit EVEX predicate
removed that invalid selection.

The next version ran but failed official vectors once the four-chunk path became
hot. All four rotate counts passed a standalone C2 oracle, and the complete
suite passed with OSR disabled. That isolated the problem to the multi-
instruction rule's allocator contract. Marking both the destination and helper
register as temporary, and computing the helper shift before a potentially
aliased destination write, made normal and OSR compilations correct.

Final gate: all **542** forced `scratchChunkVector=true` conformance tests pass
on the experimental Java 28 VM with Rust present and normal OSR enabled. The
suite covers ordinary, keyed and derive-key hashing, XOF, offsets, reset,
repeat finalization and incremental boundaries.

## Machine code

The final stable non-OSR C2 body is 7,864 bytes. Its round-loop body contains:

| instruction | static count | role |
|---|---:|---|
| `vpshufb` | 16 | eight ROR16 plus eight ROR8 |
| `vpsrld` | 16 | ROR12/ROR7 right halves |
| `vpslld` | 16 | ROR12/ROR7 left halves |
| `vpor` | 16 | ROR12/ROR7 joins |

Each shuffle is a single RIP-relative memory-source instruction naming either
`vector_int_ror8_shuffle_mask_stub` or
`vector_int_ror16_shuffle_mask_stub`. This is the intended Rust-like rotate
shape. The annotated capture is `build/e019-avx2-ror-perfasm.log`.

## Exact four-chunk kernel

CPU 3, two forks, 5x1 s warmup and 5x1 s measurement, JMH `perfnorm`:

| metric per four-chunk batch | baseline JDK | AVX2 ROR JDK | change |
|---|---:|---:|---:|
| time | 4,385.083 ns | **3,601.035 ns** | **-17.9%** |
| cycles | 12,207.270 | **10,137.928** | **-17.0%** |
| instructions | 37,635.221 | **36,880.109** | -2.0% |
| branches | 2,486.581 | 2,483.632 | neutral |
| IPC | 3.083 | **3.638** | +18.0% |

The cycle gain is much larger than the retired-instruction reduction. Replacing
three dependent instructions with one shuffle shortens the compression
dependency chains as well as removing work; the N97 consequently sustains more
IPC. Cache events remain negligible in this exact in-cache probe.

Allocation remains at the profiler floor: 0.021 B/op with zero collections.

## End-to-end 8 MiB diagnostic

CPU 3, one fork, 3x1 s warmup and 3x1 s measurement. These are shorter
composition checks; the exact-kernel counter run above is the stronger causal
measurement.

| shape | baseline Java | AVX2 ROR Java | change | Rust | Java / Rust |
|---|---:|---:|---:|---:|---:|
| one-shot | 817.1 MiB/s | **941.1 MiB/s** | **+15.2%** | 1,689.2 MiB/s | 55.7% |
| reused | 841.5 MiB/s | **909.9 MiB/s** | +8.1% | 1,646.6 MiB/s | 55.3% |
| streaming 4 KiB | 788.0 MiB/s | **932.2 MiB/s** | **+18.3%** | 1,076.3 MiB/s | 86.6% |

The reused experimental run has visibly higher iteration variance, so its 8.1%
figure is directional. One-shot and streaming agree with the 17.9% exact-
kernel improvement. The first combined launch omitted the Vector module from
JMH child forks; its Java failures are harness errors, while its Rust numbers
remain valid and were paired with the corrected Java-only launches.

## Decision and next experiment

Accept the compiler experiment as strong positive evidence. It is the first
compression change since E014 that is correct, allocation-free, smaller in
dynamic work, and materially faster in the production-sized kernel. It does
not change FastBlake Java source or production dispatch; the JDK worktree is
still an experimental VM patch and needs dedicated HotSpot regression tests
before it can be treated as generally safe.

The next FastBlake experiment should retest the 256-bit preferred-width kernel
on this VM. E013's eight-lane kernel was only 2.5% behind the four-lane kernel
before byte-aligned rotates became single instructions, and this rule already
supports AVX2 YMM vectors. Gate it in the same order: official vectors,
allocation, stable hdis, exact-batch counters, then end-to-end Java/Rust. If
256-bit remains slower, resume instruction-class accounting on the 128-bit
kernel rather than changing Java source structure again.

Resolved by E020: the exact eight-lane kernel is 4.7% faster per byte on the
patched VM, but it is also 5.2% faster on the stock VM. The lowering benefits
both widths by about 20%; it does not specifically change the exact-kernel
width trade-off. See `reference/performance/results/e020-n97.md`.
