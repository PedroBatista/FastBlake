# E020 Intel N97 preferred-width retest on the AVX2-rotate VM

Date: 2026-08-06  
Environment: Intel N97, Linux, CPU 3 pinned,
`kernel.perf_event_paranoid=2`, AVX2 (`UseAVX=2`, `MaxVectorSize=32`). The
unmodified image is `/opt/jdk-28-custom`; the E019 image is
`/home/pedro/bin/jdk/jdk/build/linux-x86_64-server-release/jdk`. Both identify
as OpenJDK 28-internal from source revision `c61f5b7ad8f`.

## Scope and public-library constraint

E019 proved that changing C2 to lower constant packed-int ROR8/ROR16 to AVX2
`vpshufb` materially improves the four-lane kernel. E020 asks whether E013's
eight-lane/YMM kernel becomes preferable under that lowering.

This is deliberately a compiler research result, not a FastBlake release
candidate. FastBlake is a public library and cannot ask users to install a
private HotSpot build. A result is practically promotable only if it works on a
stock supported JDK, is expressible in library source, and passes correctness,
allocation, machine-code, and composed-throughput gates.

No production source was changed. The only code addition is a JMH method that
calls the real `Blake3ChunkVectorWide.hashChunks` kernel, including message
loading, sixteen block compressions, chaining, and CV extraction. It permits a
direct comparison with `completeFourChunkBatch`, normalized for 8 KiB versus
4 KiB of useful input.

## Correctness and allocation

The complete 542-test conformance suite passes with
`fastblake.experimental.wideChunkVector=true` on the patched VM, normal OSR,
and the Rust contender present. It covers ordinary, keyed and derive-key
hashing, XOF, offsets, reset, repeat finalization, and incremental boundaries.

The exact kernels remain at the JMH GC-profiler floor with zero collections:

| exact call | useful input | allocation |
|---|---:|---:|
| four lanes | 4 KiB | 0.021 B/op |
| preferred/eight lanes | 8 KiB | 0.039 B/op |

The doubled floor value follows the roughly halved operation rate; neither
kernel has input-proportional allocation.

## Exact 2x2 counter comparison

Each VM ran both methods on CPU 3 with two forks, 5x1 s warmup, 5x1 s
measurement, and JMH `perfnorm`. Values below are normalized per KiB of input,
so the eight-lane call's twice-larger batch cannot look faster merely by doing
twice the work.

| metric per KiB | stock 128-bit | stock 256-bit | patched 128-bit | patched 256-bit |
|---|---:|---:|---:|---:|
| time | 1,026.350 ns | **972.755 ns** | 817.994 ns | **779.890 ns** |
| cycles | 3,071.574 | **2,928.659** | 2,536.815 | **2,315.639** |
| instructions | 9,475.159 | **5,258.999** | 9,258.347 | **5,126.228** |
| branches | 626.196 | **330.301** | 622.980 | **329.160** |
| IPC | 3.085 | 1.796 | 3.650 | 2.214 |

Width result:

- stock JDK: eight lanes are **5.2% faster per byte**;
- patched JDK: eight lanes are **4.7% faster per byte**;
- patched-versus-stock time improves 20.3% at four lanes and 19.8% at eight;
- patched-versus-stock cycles improve 17.4% and 20.9%, respectively.

The new lowering therefore does not uniquely unlock the 256-bit kernel. It
removes essentially the same rotate dependency chains at both widths. YMM
already saves almost half the instructions and branches per KiB because the
same vector graph processes twice the lanes, but the N97's IPC falls sharply at
256 bits. That throughput limit turns a theoretical doubling into a measured
roughly 5% exact-kernel gain.

This exact result also clarifies E013's older 2.5% end-to-end width loss: the
kernel itself had a small width advantage, while update/tree composition and
measurement noise were sufficient to reverse the complete-hash result.

## Machine code

The stable wide compilation uses YMM operands throughout. Its hot round body
contains the intended rotate split:

| instruction | static count | role |
|---|---:|---|
| `vpshufb` | 16 | eight ROR16 plus eight ROR8 |
| `vpsrld` | 16 | ROR12/ROR7 right halves |
| `vpslld` | 16 | ROR12/ROR7 left halves |
| `vpor` | 16 | ROR12/ROR7 joins |

The `vpshufb` instructions name the E019 ROR8/ROR16 compiler-stub masks and use
RIP-relative memory sources. `Blake3ChunkVectorWide.hashChunks` accounts for
98.2% of sampled cycles. The annotated code still contains frequent YMM
loads/stores to `%rsp`, so doubling width does not remove register-pressure and
spill costs.

## 8 MiB composition diagnostic

CPU 3, two forks, 5x1 s warmup and 5x1 s measurement:

| shape | patched four-lane route | patched eight-lane route | Rust | eight / Rust |
|---|---:|---:|---:|---:|
| one-shot | 909 MiB/s | **1,020 MiB/s** | 1,658 MiB/s | 61.5% |
| reused | 898 MiB/s | **998 MiB/s** | 1,647 MiB/s | 60.6% |

The eight-lane means are 12.2% and 11.1% higher. Treat this as a directional
composition result: iteration variance is much wider than in the exact kernel,
and the current four-lane pending-buffer path and old wide update path are not
structurally identical. The exact 4.7% normalized result is the causal width
measurement.

The wide path has no E016-style pending batch for incremental input. A short
4 KiB streaming diagnostic therefore remains scalar and measures 398 MiB/s;
this is a routing limitation, not wide-kernel throughput.

## Practical decision

Do not promote either SIMD path from E019/E020 and do not make a custom VM a
FastBlake requirement. The compiler experiment is valuable because it assigns
a concrete payoff to a missing stock-JDK lowering and supplies an exact HotSpot
case, but users of the library cannot receive that payoff today.

E016 already tested the available library-only expression. Isolated
`ByteVector.rearrange` ROR8/ROR16 probes correctly lowered to one `vpshufb` and
were more than twice as fast. Inserting only the ROR16 form into the real
four-lane kernel, however, allocated **205,426,540 B per 8 MiB hash** and cut
throughput from 774 to 245 MiB/s. Its wrapper graph crossed C2's escape-analysis
cliff, so it is not a usable source-level workaround.

The deployable position is consequently unchanged:

- retain ordinary `VectorOperators.ROR` in library source;
- keep four- and eight-lane kernels opt-in;
- require a stock-JDK, allocation-free, end-to-end win before changing public
  dispatch;
- retain E019/E020 as quantitative evidence for an upstream HotSpot lowering,
  which would let unchanged FastBlake source benefit on a future stock JDK.
