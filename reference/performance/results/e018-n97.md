# E018 Intel N97 partial-unroll experiment

Date: 2026-08-06  
Environment: Intel N97, Linux, custom OpenJDK 28-internal with hdis, AVX2,
`kernel.perf_event_paranoid=2`.

## Question

E017 showed that compression accounts for about 85% of the four-chunk
kernel's instructions and that Java retires 4.28 times Rust's instructions per
8 MiB hash. E018 asks whether source-level partial unrolling can remove round
loop, schedule and range-check work without crossing the known Vector API
escape-analysis cliff.

All variants execute the same seven BLAKE3 rounds over 16 named 128-bit state
vectors and reusable primitive message scratch. The benchmark constructor
checks every candidate's checksum against the compact-loop control before JMH
starts measuring.

## Automatic-unroll screen

Raising C2's `LoopUnrollLimit` from its default 60 through 90, 120, 180 and 240
did not provide a useful result. All five quick runs remained effectively
allocation-free, but their timings ranged from 238 to 295 ns with no monotonic
improvement. C2 does not turn this large Vector API round body into a useful
partial unroll merely by raising the global heuristic.

Raw results: `build/jmh-jdk28-e018-looplimit-{60,90,120,180,240}.json`.

## Static-copy escape-analysis boundary

A conventional 2x loop plus a peeled seventh round contains three static
copies of the round body. That is already too large: steady iterations allocate
about **43,776 B/op** and repeatedly deopt/recompile. A 3x loop plus the peeled
tail contains four copies and also allocates about 43,775 B/op. This sharpens
E011's result: on this JDK the failure is not unique to seven fully expanded
rounds; three static round-body copies are sufficient.

The only remaining 2x shape uses two static copies and guards the odd tail:

```text
for (round = 0; round < 7; round += 2) {
    roundBody(SCHEDULE[round]);
    if (round == 6) break;
    roundBody(SCHEDULE[round + 1]);
}
```

The text above is structural pseudocode. The actual benchmark keeps all state
in named `IntVector` locals and duplicates the round expressions in source.

## Isolated guarded result

CPU 3, two forks, 7x1 s warmup and 5x1 s measurement, JDK 28 `perfnorm`:

| one seven-round block | compact loop | guarded 2x | change |
|---|---:|---:|---:|
| time | 239.551 ns | 227.476 ns | **-5.0%** |
| cycles | 696.553 | 688.357 | -1.2% |
| instructions | 1,992.253 | 1,942.033 | **-2.5%** |
| branches | 139.456 | 136.215 | -2.3% |
| branch misses | 0.0115 | 0.0137 | negligible |
| IPC | 2.860 | 2.821 | -1.4% |

Both paths allocate effectively zero. The small instruction/branch reduction
is real, but it also bounds the opportunity: round-loop and schedule control
are only a few percent of the remaining compression instruction count.

hdis explains the candidate's risk. The stable non-OSR C2 body grows from
4,720 bytes for the compact loop to **20,872 bytes** for the guarded form, while
both retain a 320-byte frame. Two source bodies expose a much larger Vector API
compiler graph even though escape analysis still succeeds in isolation.

Raw results: `build/jmh-jdk28-e018-final-counters.json`,
`build/e018-loop-hdis.txt`, and `build/e018-guarded-hdis.txt`.

## Full-kernel integration gate

The guarded form was temporarily inserted into the actual
`Blake3ChunkVectorScratch.hashChunks` method and passed the full forced
scratch-vector conformance suite, including ordinary, keyed, derive-key and
incremental cases. It also remained effectively allocation-free.

The same-command exact four-chunk benchmark nevertheless rejects it:

| complete four-chunk kernel | compact restored | guarded integrated | change |
|---|---:|---:|---:|
| time | 4,286.171 ns | 6,515.209 ns | **+52.0%** |
| allocation | 0.027 B/op | 0.041 B/op | profiler floor; zero GC |

The isolated 5% round win does not compose into the already-large production
kernel. Code growth and the resulting C2 machine-code quality cost far more
than the saved loop instructions. The production method was restored exactly;
E018 leaves no production behavior change.

Raw results: `build/jmh-jdk28-e018-integrated-kernel-gc.json` and
`build/jmh-jdk28-e018-restored-kernel-gc.json`.

## Decision

Reject Java-source partial unrolling. Keep the variants only as diagnostic JMH
controls. E018 closes loop bookkeeping as a major explanation for the Java/Rust
gap: the best allocation-free isolated form removes only 2.5% of instructions,
and integration regresses the real kernel by 52%.

The next compression experiment should remove instructions without duplicating
the Vector API graph. The highest-value route is now a custom-JDK compiler
experiment: lower constant packed ROR8/ROR16 to `vpshufb` on AVX2 inside C2,
then re-run E016's hdis, allocation, full-kernel and Java/Rust counter gates.
That attacks repeated machine instructions while keeping the compact Java
source shape that escape analysis requires.
